# 知行 0.12.11 · 窗口不再等自动化与服务

`0.12.10` 定位到 `initialise` 占启动约八成。本轮把它拆开：自动化状态与浏览器、终端、语音三个面板服务不在首帧之前完成。

## 改动

- **自动化状态移出首帧路径。** `AutomationService` 仍在 `initialise` 内构造，但其 `initialise()`（读盘、校验、写回）与建窗并行进行；窗口显示后才等待它，再启动调度。
- **面板服务改为首次使用时准备。** 浏览器、终端与语音服务不再在 `initialise` 中构造，而是在窗口显示后后台准备；任何 `browser:`、`terminal:`、`speech:` 通道先等待同一个就绪 promise。
- **通道守卫集中在 `handle`。** 按 channel 前缀判断，`automation:` 等自动化就绪，`browser:`／`terminal:`／`speech:` 等服务就绪，避免二十多个 handler 各写一遍。
- **退出仍等自动化。** `before-quit` 在关闭自动化前先等其就绪 promise，避免半初始化状态被关闭。

## 实测

Windows x64 目录包、空档案冷启动，10 次取中位数：

| 指标 | 0.12.10（5 次） | 0.12.11（10 次） |
| --- | --- | --- |
| `initialise` 完成 | 1,017 ms | 913 ms |
| 窗口显示 | 1,131 ms | 1,044 ms |
| 可交互 | 1,281 ms | 1,226 ms |

阶段（本轮中位数）：导入 163 ms、状态 609 ms、内核 615 ms、自动化构造 913 ms，`initialise` 返回 913 ms；窗口显示 1,044 ms；面板服务在窗口显示后约 85 ms 完成准备（1,129 ms）。

也就是约 100 ms、8%，但**没有做同环境交替对比**，两个版本的测量间隔约一小时，而 Windows 单次启动波动可达数百毫秒，因此该数字接近噪声下限，只作方向参考，不作为显著提速宣称。

## 守卫验证

新增一次性核对：应用启动、preload 桥接可用后立刻并行调用三个被延迟的通道——`automation:list`、`browser:state`、`speech:status`，三条都在窗口刚出现时返回正常结构（4–7 ms，返回 `revision:1` 的空自动化、`office-home:home` 的空浏览器状态、SenseVoice 状态），没有因为服务尚未就绪而失败。

## 仍然存在的成本

延迟只是把工作移出首帧，主线程的模块导入与同步解析照旧发生。本轮之前已实测：把十八个模块导入改成并行批次，导入阶段从 173 ms 变成 1,072 ms，整体慢约 240 ms，已回退。要继续压缩启动，需要减少模块加载本身的成本（拆分模块或引入编译缓存），而不是调整顺序。
