# 知行 0.32.0 · `ENOTFOUND` 文案收口（P0-1）

## 解决什么问题

「解析不到服务地址，请检查网络连接或代理设置。」这条文案从 0.14.1 就写在映射表里，但**连续两版都没有真正触发过**：本机的 DNS 把所有普通域名（包括 `.invalid`）解析到代理的 fake-IP 段，请求在连接阶段就被重置，拿到的错误码是 `ECONNRESET` 而不是 `ENOTFOUND`。于是「DNS 失败已验证」一直是虚的。

## 怎么改

只改验收脚本 `scripts/test-error-copy-ui.mjs`，产品代码不变：

1. **造一个真实的解析失败**：主机名标签超过 63 个字符时，`getaddrinfo` 直接返回 `ENOTFOUND`——这不是伪造错误码，是一次真正的解析失败。用例改为 `https://<64 个 a>.invalid/v1`，并**断言拿到的就是 `ENOTFOUND`**，环境一变就报错而不是悄悄降级。
2. **保留对照用例**：普通 `.invalid` 在本机会被本机 DNS／代理接住，实际得到 `ECONNRESET`；这条也保留，按实际错误码断言对应文案，并在用例名里写明真实码。
3. **401 用例加重试**：本机网络偶发丢包（本次实测出现过 `ECONNRESET`），真实 401 探测最多重试 4 次、间隔 5 秒，仍拿不到 `HTTP_401` 就失败——不把网络抖动当成产品结论。
4. **日志断言改成按实际用例数**：原来写死「四次拉取失败」和固定四条正则，加了用例就崩；现在按 `observed` 用例数与被观测到的原因逐条比对。

## 结果

- Windows 实包层：`npm run test:errors` **6/6 通过**，其中新增的关键一条——
  `解析不到的主机显示「解析不到服务地址」（ENOTFOUND）显示「解析不到服务地址，请检查网络连接或代理设置。」`
  主进程日志同时保留带真实错误码的技术句（`读取模型列表失败（ENOTFOUND），已保留当前配置。`），界面不搬技术原文。
- 其余五条：真实 401（`api.deepseek.com` + 假 Key）、被本机网络接住的 `ECONNRESET`、`ECONNREFUSED`、12 秒 `TIMEOUT`、以及「主进程保留真实错误码、每条界面文案都与技术原文不同」。
- 源码层与其它实包门禁见 `acceptance-summary-0.32.0.json`。

## 边界

- 这条 `ENOTFOUND` 来自「标签过长导致 `getaddrinfo` 失败」，不是「域名不存在（NXDOMAIN）」；两者在 Node 里是同一个错误码，但**解析器的具体成因不同**。文案本身面向「解析不到」，覆盖两种情况；如果要单独证明 NXDOMAIN，需要一个能返回 NXDOMAIN 的解析器，本机被代理接管，做不到。
- 401 用例依赖真实访问 `api.deepseek.com`：网络中断时即使重试也可能失败，此时脚本会明确失败而不是跳过。
- 本机网络行为（fake-IP 代理）会变：脚本对「对照用例」的错误码不做硬编码，只要求它在映射表里；`ENOTFOUND` 用例则新增了硬断言，环境变化会立刻暴露。
- 本轮**没有**重跑其它实包套件（改动只涉及错误文案脚本），也**没有**真实云端证据。
- 安装生命周期仍是 0.24.0 的 53 步证据；安装包未签名；首次内容绘制仍为 `null`。
