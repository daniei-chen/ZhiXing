# 知行 0.37.0 · 型号换了，窗口跟着换

## 解决什么问题

0.36.0 验收时在界面上看到一处自相矛盾：模型入口已经写着「QA 中窗口」，输入区的用量却还写着 `上下文 12,792 / 131,072 tokens`——分母是上一个模型的窗口。要等到新模型的第一次请求真正发出去、内核回报新的压力口径之后，分母才变成 32,768。

用户在这个空档里看到的是两次互相打脸的读数：同一个界面既说当前是中窗口模型，又说窗口有 131,072。如果这时点「压缩上下文」，或者据此判断「还装得下」，都是错的。

## 怎么改

输入区那句用量的分子来自内核实测（`message.context.measurement.totalTokens`），分母原先取 `message.context.pressure.contextWindow`——那是**上一次真正发出请求时**用的模型窗口。改成按「当前选中的型号」取，优先级与主进程构造请求时完全一致：

1. 型号自己声明的 `contextWindow`（0.34.0 起由 `modelLimits` 从目录里读出来）；
2. 供应商声明的 `contextWindow`；
3. 上一次实测的压力口径；
4. 都没有时用 128,000（和原来的兜底一致）。

规则抽在纯函数模块 `src/context-window.js`（`modelContextWindow`／`contextWindowTokens`／`contextUsageText`），界面只负责把 `runtime` 与 `state.settings` 传进去。同名型号出现在两个供应商下时按「供应商 + 型号」精确匹配，不靠名字猜。

## 结果

- 源码层：新增 `tests/context-window.test.mjs` 6 个用例（型号优先、同名按供应商区分、退回供应商、退回实测、全未知用 128,000、文案排版），`npm test` 505 项、504 通过、1 跳过、0 失败。
- Windows 实包层：`npm run test:model-switch` **5/5**，新增的第 1 例在**点完型号、还没发请求**的时刻断言用量已经显示 `32,768`；若把这次改动回退，断言会拿到 131,072 并失败。其后四例照旧跑通（压缩 → 提交 → 答复 → 用量一致）。
- 同一实包上 `npm run test:model-window` 4/4（失败路径未回归）、组件 14/14、站点 4/4、打包 354 项。

## 边界

- 只改分母。分子仍是上一次实测的历史大小——换型号不会让历史变小，所以这个数在本轮里不变是正确的，但它**不是**为新窗口重新测量过的值；要等新请求回来才会刷新。
- 型号目录里若既没有型号级窗口、也没有供应商级窗口，界面会退回到一次实测值（或 128,000），这时分母可能仍与实际窗口不一致——`modelLimits` 只在目录声明了字段时才写窗口，没有声明的供应商属于这种情况。
- 只验证了「切换后立刻显示」这一条界面口径；没有验证窄窗口下的换行、字号与截断（仍是文本断言）。
- 极小窗口（8,192）压缩不收敛的问题不在本轮范围，行为未变。
- 图像卸载、真实云端、签名、安装生命周期仍未覆盖（生命周期仍是 0.24.0 的 53 步）。
