# 知行 0.36.0 · 切换压缩的成功路径终于有了证据

## 解决什么问题

0.34.0 把上下文窗口做成跟着型号走，从此「换到窗口更小的型号」会真的先压缩；0.35.0 又把失败时的文案说清楚了。但这两版都只证明了「先压缩、不静默超额发送」和「压缩不成会说清」——**从来没有一次证明它压得成**。切换压缩一直是「已知会失败、失败会说清」，而不是「能成功」。

这条空白不是没试过。0.34.0 的假历史里每轮塞约 6,750 tokens 的填充文本、单条回答就有约 2,850 tokens；切到 8,192 窗口的型号后，内核第一次压缩把前缀压成检查点（约 103 tokens），可**保留的 16% 尾巴本身就已经高于 3,072 的阈值**，于是第二次压缩只能拿检查点自己去摘要，被「summary is not smaller than the shadowed content (103 >= 103)」拒绝。当时把这句记成「合成环境不可达」，其实是没算清这笔账。

## 怎么改

这版**没有改产品代码**。改的是验收：新增 `scripts/test-model-switch-ui.mjs` ＋ `npm run test:model-switch`，在打包 EXE 上走完整条路径。

关键在于把历史的形状算对。窗口 W、输出上限 M 时，知行自己的策略会收缩 headroom：

- 预算 = W − M
- headroom（收口后）= max(1024, ⌊预算 / 2⌋)
- 阈值 = min(0.8·W, 预算 − headroom) = ⌊预算 / 2⌋
- 保留尾巴 = ⌊预算 × 0.16⌋

压缩后留在地面上的三块是「固定开销（系统提示 + 工具定义）＋ 检查点（约 103）＋ 保留尾巴」。要让它落到阈值以下，必须满足 **固定开销 + 保留尾巴 + 103 < 阈值**。8,192 窗口时阈值只有 3,072，而固定开销实测就有约 4,600 tokens，任何摘要都救不回来——这才是「不可达」的真正原因，是窗口太小，不是合成环境的问题。

于是门禁用 **32,768 窗口 / 8,192 输出**：预算 24,576、阈值 12,288、保留尾巴 3,933，压缩后约 8,600 < 12,288，一次压缩就能收敛。历史用 5 轮、每轮约 2,700 tokens（5 轮 × 2,700 ≈ 13,500 > 12,288），刚好越过阈值。

## 结果

Windows 实包（`0.35.0` 的构建，证据目录 `model-window` 同级的 `model-switch/run-mwx24e9f`）**4/4 通过**，实测请求序列：

| 阶段 | 请求 | 模型 | 消息数 | 字节 |
| --- | --- | --- | --- | --- |
| 切换前最后一轮 | 正常提交 | `qa-big` | 11 | 65,200 |
| 切换后第一次 | 压缩（摘要） | `qa-big` | 12 | 67,070 |
| 随后提交 | 正常提交 | `qa-small` | **7** | **44,870** |

- 压缩请求与提交请求是先后两条，中间没有别的请求，也没有把 13,500 tokens 的历史原样塞进 32k 窗口；
- 提交比压缩请求少 5 条消息、少 22,200 字节（约 33%），说明被替换的区间确实换成了检查点；
- 界面多出一轮正常答复，正文无「运行错误」，`errorText` 为空；
- 用量显示 `上下文 12,792 / 32,768 tokens`，与切换后的型号一致（切换前它显示的还是旧窗口 131,072，见边界）。

写这个门禁时踩到三个坑，都记进了 `AGENTS.md`：

1. **运行中的发送按钮 aria-label 会变成「停止生成」**，输入框却仍可编辑，只查 `disabled` 会在一轮没跑完时又发一轮，主进程直接回「该会话正在运行」并让整轮收尾失败；
2. **答复气泡在压缩阶段就已经出现**（显示「思考中」），按气泡数量等答复会在请求还没发出时就继续断言，必须等真正的请求到达、并且正文不再是「思考中」；
3. **模型浮层要逐级打开**，点 `.model-trigger` 后 `.effort-model-link` 不一定立刻出现，得等目标出现，没开出来就 Esc 重来。

## 边界

- **产品代码一行未改**。这版交付的是证据与门禁，不是新能力；凡是「切换压缩已修好」的说法都不成立——它本来就是这个行为，只是此前没有证据。
- **8,192 这类极小窗口仍然压不成**：阈值 3,072 小于固定开销（约 4,600 tokens），数学上无法收敛。0.35.0 的文案会告诉用户「换更大的模型或新建聊天」，这是目前正确的处理；本轮**没有改**小窗口的保留比例或阈值口径，因为那会偏离桌面版的 `retainRatio 0.16`／`thresholdRatio 0.8`。
- 切换完成后、请求发出前的那一瞬间，输入区的用量仍显示**旧型号的窗口**（实测 131,072），成功之后才变成 32,768。这是本轮发现的显示口径缺陷，**未修**。
- 只验证了「历史略高于阈值、一次压缩即收敛」这一种形状；多轮反复压缩、图像卸载、真实厂商的 usage 形状都未覆盖。
- 合成服务不回报 `usage`：一旦回报，`prompt_tokens`（整段请求的累计值）会被内核记到节点上，把保留尾巴撑到阈值以上，压缩同样收敛不了——这是合成数据形状的限制，不是产品行为，但**真实厂商的用量形状是否会导致同类问题，本轮没有验证**。
- 门禁在长会话下会撞到知行自己的「无法确认内核已退出，已保留会话恢复文件」：实测 18 轮、每轮很短时在第 8–9 轮出现，5 轮、每轮较长时不出现。触发条件未查实，本轮用减少轮次规避，并在验收里写明。
