## 子任务中断：同阶段两处确定性复现

在真实 Harness 和 loopback 模型服务中分别延迟子 Agent 建立与控制桥文件落盘，复现了两个相互独立的生产竞态：

1. 上游 `subagent.started` 是 `session/created` 的投影，不是 Agent 已进入运行轮次。只将子 Agent 创建过程延迟 800 ms，知行已发出 `running`，控制也返回 `{requested:true}`；但原生 `session.status=running` 在其后约 790 ms 才到达，子任务随后仍发出模型请求并等待。按上游真实 `running` 再中断的对照正常得到 `aborted`，父轮次也正常完成。
2. 只延迟控制桥文件落盘 5 秒，子任务 `running` 已可见但控制文件尚不存在；控制请求立即失败，故意等待的子模型请求继续占住父轮次。启动流程没有等待控制桥，构成独立就绪缺口。

原生中断只作用于已存在的活跃轮次，知行不能把会话创建误标为可中断的运行状态。修复应以原生 `session.status` 开放控制，并将控制桥就绪纳入有界、可取消的等待；测试也须并行观察控制失败，不能先等待被故意挂起的主任务再检查控制 Promise。旧 Windows 日志没有记录这两处关键时序，无法断言第二轮具体触发了其中哪一个；上述结论来自独立的受控复现，不补写旧证据。

就绪范围还需区分插件与宿主：让 `execution-controls.apply()` 返回其 `ready` Promise，只能让 Cordis 等待该插件，真实探针表明并行启动的 SDK server 仍可能先可用。因此运行时还须在 `h.start()` 之后、任何 `session.run()` 之前显式等待控制桥；超过 4 秒或取消就结束本次启动，不先向模型发出任务。单次控制请求的文件等待与 HTTP 则共用另一条原有 4 秒请求预算，不能因重试读取文件重新计时。

第三候选提交前的 Linux 源码聚焦组为 **34/34**，无失败、取消或跳过：新增控制回归 7 项、原生技能及双协议子 Agent 3 项、清理 5 项、收尾 19 项。将相同新增 7 项测试指向 `59973ab` 的旧产品，实际得到 **5 失败、2 通过**，保留了能识别旧缺陷的反例。修复后的真实内核探针在子 Agent 创建延迟 800 ms 时正常中断并收尾；控制桥落盘延迟 2 秒时，主机等待就绪后才发出父模型请求，子任务也正常中断。该组不是 Windows 验收，仍需新候选实包门禁。

有界事件记录保存在 [subagent-controls](subagent-controls/)：`before-*` 是旧实现的创建延迟 800 ms、控制桥延迟 5 秒及对照；`after-ready-only-*` 记录仅返回插件 Promise 尚不足的中间实现；无前缀的两个文件是最终修复后的创建延迟 800 ms 和控制桥延迟 2 秒对照。仅记录事件、相对毫秒、状态和计数，没有模型请求正文、凭据或用户文件。
