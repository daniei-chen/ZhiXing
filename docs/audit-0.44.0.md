# 0.44.0 审计：对标 Harness 桌面版与同类 Agent 的问题清单

2026-11-27。本轮用户要求：全面审计应用与 DeepSeek Harness 桌面版及其他 Agent 的差距，指出可升级之处与问题，并着手修改。

审计依据是**本仓库锁定的上游源码**（`node_modules/@deepseek-ai/*`，`0.2.2-rc.5` 与锁定版本）与当前产品代码；没有重新取得用户 D 盘安装的桌面包或当前窗口，因此凡涉及「桌面版现在长什么样」的判断一律记「未核对」。

## 结论摘要

一行话：**能跑通主流程，但还缺少「像成熟 Agent 那样连续工作」的三件事——运行中继续交代、跨会话检索、进程常驻。** 前两件影响每天的手感，第三件决定长会话与非办公任务的稳定性。

## 本次已修

### 1. 运行中发不出第二条消息（缺陷）

`submit()` 里 `await startReply(...)` 一直等到整轮运行结束才 `setBusy(false)`，而 `startReply` 内部又 `await` 了主机的完整结果交接。后果：

- `busy` 在整个运行期间为真，输入区一直显示「正在读取资料或准备发送」；
- `Composer` 的 `ready` 条件包含 `!busy`，所以 Enter 与发送按钮都无效；
- `submit()` 开头也有 `busy` 早退，排队逻辑无处落地。

这不是「设计成只能等」，是状态机漏了一个 finally 边界。修法是把 `busy` 收窄为「正在准备发送」：提交阶段结束就释放，运行本身由 `running` 表达。同一处顺带修掉了「运行中再点一次会静默无反应」的手感。

### 2. 运行中排队（对标 Harness 的默认行为）

上游 `dsh-client-ui-conversation` 的 `busyEnter` 默认值是 `queue`，界面文案为「排队发送」「{n} 条排队消息」「删除排队消息」，运行中按 Enter 即入队，本轮结束后按顺序发出。知行此前没有这一层。

本轮实现（`src/message-queue.js` + `src/App.jsx`）：

- 运行中提交进入队列，**不打断当前交办**，也不另起内核；
- 队列按聊天隔离，只有当前聊天、当前工作空间的队头会被发送；
- 队头发送前重新做一次完整校验（供应商、型号、思考档位、隐私模式、命令附件），与直接发送同一条路径；
- 队头失败时整条队列停住，错误就地显示、可重试，不会让后面的消息越过失败项继续执行；
- 可编辑（内容回到输入框）与删除；
- 通过 `onAccepted` 在「消息锚点已落盘、内核已接手」之后才把队列项移走，避免「既没在队列也没在运行」；
- 排队内容随加密工作空间保存（`queuedMessages`），刷新或重启后回来仍显示，并标为「上次退出时未发送。请确认后重试。」，不会自动重放。

**边界**：这是排队，不是插话。上游还支持把排队消息「插话发送」进正在运行的一轮（`queue.steer`、`Ctrl/Cmd+Enter`），知行未做，见下文第 10 项。队列是界面层账本，不写进模型上下文，也不跨主进程重启恢复运行。

### 3. 会话标题未清控制符（缺陷）

新聊天标题原来是 `draft.text.replace(/\s+/g,' ').slice(0, 42)`：既不按字节（会把 emoji 或组合序列截成半个码点），也不清控制符。上游 `dsh-session-title` 的 `normalize.js` 明确写着「方向与不可见控制符会让显示的标题具有欺骗性」，并按 UTF-8 字节预算截断。

新增 `src/session-title.js`，逐条沿用上游的四组模式（OSC、CSI、ESC、C0/C1 与方向控制符），先清再按字节截断，超长补省略号。空标题回退「新的交办」。规则例外已在 [质量门禁](code-quality.md) 第 3 条登记。

## 发现但本轮未修

### 4. 每轮新建并关闭内核（最大架构差距）

`electron/runtime.mjs` 的 `run()` 每次 `createHarness(...)`（第 595 行）并在结束后 `closeHarness`（第 783、789 行）；`check()` 也一样。这意味着：

- 每一轮都要冷启动子进程、重新握手、重新连接 MCP，首字延迟与「第二轮莫名变慢」都来自这里；
- 长会话、多轮工具调用的稳定性受进程生命周期约束，`cleanup_pending` 隔离就是它的副作用。

上游 SDK 的 `DeepSeekHarness.start()` 本身缓存初始化 Promise、支持复用（`dsh-sdk-client/lib/types/api.d.ts`），所以不需要新造协议；缺的是知行这边的常驻宿主设计与隔离契约（凭据、工作区、脱敏保险库、桥接密钥、审批闭包、取消信号都不能串轮）。路线与验收口径已在 [成熟化路线](maturity-roadmap.md) 2A 写清，本轮不动。

### 5. 会话历史检索

两个层面都没有：

- 模型侧：上游有 `dsh-tool-session-query`（参数含 `query`、`session_ids`、`created_at_from/to`、`parent_session_ids`），配合 `dsh-session-query-sqlite` 做历史全文检索；知行未挂载（`electron/runtime.mjs` 里没有 `session-query`）。
- 界面侧：`src/Dialogs.jsx` 第 39 行的搜索是 `scope.chats` 的标题加正文子串匹配，范围是当前工作空间、不含归档，没有片段、没有命中定位。

结果是「上周那份纪要」只能靠记忆翻侧栏。这是 Harness 与 Codex 这类产品最先被用到的高级能力之一，建议下一轮做，但要注意：知行历史是加密文件，先要决定索引放在哪、加密与否，再接模型工具。

### 6. 自动审阅（Auto Reviewer）

`dsh-experimental-auto-review` 的机制是「对每次待批调用做一次模型审阅，用审阅结论代替人工批准」，并有固定的 `REVIEW_POLICY`（低风险必须放行、中风险需当次授权、高风险一律拒绝）。知行的「帮我批准」不是这个：`harness/file-policy.mjs:105` 的 `needsApproval` 只对**项目内新建文件**自动放行，覆盖与外部写入仍逐项询问。文案与实现目前一致，但和 Harness 的 auto 语义不同，对标档位应记「部分」。

未做是有意的：自动审阅会把「是否放行」交给另一个模型，与「凭证阻断」「文件权限审批」这些硬边界的关系必须先定清楚，不能顺手打开。

### 7. `@` 文件引用

上游输入区占位文案是「发消息或创建任务, / 调用指令, @ 文件或对话」，并且有 `dsh-file-reference` 的 `@` 记号语法。知行只有 `/` 命令；想把项目里的文件交给模型，只能打开文件面板或加附件。建议做法：项目会话里 `@` 触发递归文件清单（跳过私密清单），插入相对路径文本，让模型用文件工具读取；不引入新的授权通道，仍受当前权限档位约束。

### 8. 轨迹的单条检查器与按轮次折叠

现有执行面板已能按交办切换、分类、检索、看子任务与作业。仍缺：单条记录的输入/输出检查器、单条 token 用量、按轮次折叠、TTFT／吞吐概览。注意知行的 `trace` 有意只存标签与元数据（不存工具参数与结果原文），做检查器时不能把敏感正文顺手带进可导出的事件摘要。

### 9. 交付预览只有提取文字

已发布的 0.42.0 在右侧给出提取文字与读取范围；图片、PDF、Office 原版面仍不可预览。这是渲染能力差异，不是导航差异，别混记。

### 10. 插话发送（steer）

上游区分 queue 与 steer：`Ctrl/Cmd+Enter` 把排队消息插进正在运行的一轮。知行的排队只在轮次结束后发送。做 steer 需要宿主在运行中接受新输入（`updateQueue` → `kind: steer`），与当前「每轮一个内核」的生命周期冲突，属于第 4 项之后的连带工作。

## 文档口径纠正

`docs/harness-parity.md` 的「会话日志」一行把 `dsh-client-ui-settings-session-log` 当成日志查看器，记为「未核对」。读源码后应纠正：这个包是设置项「在使用官方模型 API 时上传 Session Log」的开关，服务于改进 DeepSeek 模型，不是查看器。知行禁用 `session-log-deepseek` 是**有意的隐私偏差**，不该写成「未核对」，也不该当成待补能力。本轮已同步修正对照表。

- 源码单测：`npm run test` 在 Linux 上为 706 项 / 679 通过 / 15 失败 / 12 跳过；改动前同一命令为 691 / 664 / 15 / 12。**失败项集合完全相同**（逐项比对：语音需要 Windows x64、PowerShell PTY、Windows 沙箱与原生文件、Office/PDF 渲染、目录链接重定向），属于本机平台缺能力，不是本次回归。新增 15 项单测（排队 9、标题 4、存储恢复 2）。
- 新增随包前门禁：`npm run test:components` 增加 `tests/message-queue-ui.test.mjs`（真实 Electron renderer 里的 Composer 排队界面）与 `tests/app-queue-ui.test.mjs`（真实 App + 合成 IPC：运行中入队、本轮结束自动发出、标题控制符清理）。
- 质量门禁：`npm run quality:changed` 为 0 error / 0 warning，新增文件已按 Prettier 格式化。
- **未覆盖**：Windows 实包上的排队行为、真实模型下的排队串行、队列在崩溃/强杀后的恢复、跨工作空间切换时的队列行为。Linux renderer 通过与合成主机握手只证明界面与状态机，不等于实包验收。
