# 知行 0.13.3 · 跨版本存档兼容性

这一版没有功能改动。补的是升级路径上最容易被忽略、后果又最严重的一环：旧版本写下的存档灌进新版本，会不会丢数据。

## 为什么要补

`0.13.2` 之前，存档迁移只覆盖了 `version 1 → 2` 的历史政务空间场景。但没有测试回答过一个更基本的问题——把 `0.12.x` 写出的 `workspace.bin` 直接交给当前版本的 `mergeState`，结果是什么？自动更新一旦铺开，每个老用户升级时都会走这条路径。

于是补了 4 个用例：

| 用例 | 验证点 |
| --- | --- |
| 旧版存档缺新增字段 | 补齐 `voiceLanguage`／`personalizationEnabled`／`personalInstructions`／`privacyPolicy` 默认值；`automations`／`documents`／`appliedAutomationRuns` 为空数组；**用户自己的项目和会话正文原样保留** |
| 未知的多余字段 | 未来版本写入的新字段被安全忽略，不会让启动抛错 |
| 损坏存档 | `null`、`{}`、`version: 99`、`projects` 不是数组等五种坏输入全部回退默认状态，不抛异常 |
| 幽灵草稿 | 草稿指向已删除的会话时保留条目但不伪造归属，`chatId` 与 `kind` 保持空 |

写测试时自己先错了一次：断言旧项目迁移后 `directory` 应为 `null`，实际是继承了工作区目录。查代码后发现继承才是正确行为——旧项目没有独立目录，跟着空间走。是断言写错，不是代码有问题。

## 结果

- 源码测试 363/364（1 项受文件符号链接权限限制跳过），比上一版多 4 项。
- 目录包测试 322/323，0 失败、0 取消。
- Windows 桌面专项 5/5。
- 启动 10 次中位数：`initialise` 933 ms、窗口显示 1,035 ms、可交互 1,211 ms。

生产源码指纹与 `0.13.2` 完全一致，说明本版只动了测试与版本号，没有改运行逻辑。

## 真实升级验证

本版发布后用实际产物做了第一次真实升级演练，这是此前几个版本一直缺的一环：

1. 用备份的打包 `0.13.2`（不是源码、不是目录包里的开发版），独立临时档案启动；
2. 不设任何 feed 覆盖，直接连 GitHub，`checkDesktopUpdate()` 返回 **`available 0.13.3`**；
3. 触发下载，349 秒后状态变成 **`downloaded`**；
4. 从 `%LOCALAPPDATA%\zhixing-updater\pending\` 取出下载的安装包，字节数 338,650,183，**sha256 与发布资产 `ae1429ff…` 完全一致**。

这证明了检测、版本比较、真实网络下载、以及 `electron-updater` 的完整性校验在真实环境中全部工作。**没有做的一步是 `quitAndInstall`**——那会替换掉用户机器上正在运行的安装，主动放弃。因此「下载完成后重启安装、新版本正常启动」仍未验证。

## 生产环境的两条实测证据

发布后在一台真实安装的机器上留下了两条此前没有过的证据（`production-app-log.jsonl`）：

```
03:30:05 app.start  {"version":"0.13.2",...}
03:30:51 update.state {"status":"checking"}      ← 启动后 46 秒
03:30:59 update.state {"status":"current"}
04:25:31 app.start  {"version":"0.13.3",...}
04:26:17 update.state {"status":"checking"}      ← 又是 46 秒
04:26:27 update.state {"status":"current"}
```

两次都精确落在启动后 46 秒，验证了「启动 45 秒后后台检查一次」的设计真的按预期发生，且 GitHub 源解析、版本比较在真实安装环境下都正常。日志系统本身也在真实环境里被验证了一次。

## 安装器会先卸载旧安装

这一版踩到一个值得记录的坑：把 `0.13.2` 静默安装到一个**临时目录**做升级演练时，安装器发现注册表里已有同 `appId` 的安装，于是**先把原安装（`D:\应用\知行`）卸载掉**，再装到新位置。

这不是缺陷，是 electron-builder NSIS 的标准升级行为：安装包按 `appId` 认定「这是同一个应用」，无论 `/D` 指到哪里都会替换。教训是——**任何安装器测试都会影响机器上现有的安装**，隔离目录并不构成隔离。

这次操作把一台真实安装的环境弄掉了。补救是完整的：用户数据（`%APPDATA%\zhixing`）不受卸载影响，101 个文件与 `workspace.bin` 都在；随后用 `0.13.3` 重新安装回 `D:\应用\知行`，快捷方式与卸载项全部重建，启动正常，`workspace.bin` 1257 字节原样可读。事后还发现这让那台机器顺势升到了 `0.13.3`。

真正的教训：**`quitAndInstall` 无法在不影响现有安装的前提下验证**。下次做这件事之前，必须先完整备份安装目录、快捷方式与注册表项，再接受「卸载重装」这个既定路径。

## 边界

这些是**单元层面**的兼容性证明：直接调用 `mergeState`，喂构造出来的旧结构。真正的跨版本升级还涉及安装器替换文件、Electron 升级带来的 profile 变化、加密存储的 DPAPI 上下文，这些不是单测能覆盖的。

历史版本升级的**安装器路径**仍未跑：生命周期脚本要求基线安装器与合成档案版本一致，手上没有与本版匹配的旧版安装器档案。数据兼容性由上面的用例保证，安装行为由 `0.13.2` 的首次安装／覆盖／卸载／重装证据保证，两者拼起来覆盖了升级，但没有一次真正的「旧版装上→新版覆盖」完整演练。 [Windows 验收](windows-acceptance-0.13.3.md) · [能力地图](harness-capability-map.md)
