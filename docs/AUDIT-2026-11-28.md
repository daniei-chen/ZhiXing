## 结论摘要

- **能跑**：`npm run build` 成功，9.4 s（`index-*.js 783 kB` 超 500 kB 分块阈值告警）；`npm run electron:dist` 两次成功（26 分 48 秒 / 8 分 24 秒），产物 `release/win-unpacked` 1.3 GB、`resources/app` 48,897 个文件、`知行.exe` 246,511,104 B、Authenticode **NotSigned**；另按 `release.yml` 的同一步打出 NSIS 安装包 `ZhiXing-0.43.0-x64.exe` 338,741,253 B（252.9 s），installer / EXE / signer 三者 NotSigned，`latest.yml` 的 sha512 独立复算一致。
- **测试不绿**：`npm test` 708 例 / 687 pass / 18 fail / 2 cancelled / 1 skipped，1082 s；18 红全部是「真实 Harness」用例的 `initialize timed out after 20000ms`（14 例初始化超时 + 4 例连带断言失败），不是代码回归。`npm run test:sites` 4/4、`npm run quality` 0 error（范围 adopted+changed）、`npm run test:components` 的 17 个文件本轮未跑。
- **最重三件**：① 脱敏可被 Hangul Filler 与变体选择符绕过，手机号/身份证原样外发（D1，本机复现，PR #7 在修）；② `initializeTimeoutMs` 写死 20 000 ms，而真实启动实测 10.6–12.3 s、队长探针 20 149 ms，新建聊天后的第一次交办大概率直接失败（D2）；③ 更新链无签名锚点——安装包 NotSigned + `app-update.yml` 无 `publisherName`，运行时只剩与安装包同源的 sha512（D4）。

### A2 一条交办的链路（进 → 出）

1. `src/App.jsx:1066` `submit()`；运行中提交走 `src/App.jsx:957` `queueCurrentDraft()` 入队（`src/message-queue.js`）。
2. `src/App.jsx:1138` `desktop.prepareRun(...)` → `electron/preload.cjs:2` 暴露的桥 → `electron/main.cjs:621` `handle('agent:prepare')`。
3. `RuntimeManager.prepareRun` → `electron/runtime.mjs:595` `createHarness()` → `:210` 以 `ELECTRON_RUN_AS_NODE=1` 启动内核子进程（`DSH_HOME=临时目录`，`DEEPSEEK_API_KEY` 经环境变量注入）。
4. 内核 `session.run`（`electron/runtime.mjs:721`）；事件流由 `electron/assistant-stream.mjs` 回到渲染层。
5. 工具审批：内核 `approval/request` → `electron/runtime-approvals.mjs` → 渲染层 `src/ApprovalPanel.jsx` → `approvals:snapshot` / `answerApproval`。
6. 结果交接：`electron/runtime-handoffs.mjs`（`agent:handoffs` / `agent:await-handoff` / `agent:acknowledge-handoff`），先落盘再 ACK。
7. 落盘：渲染层 `data:save` → `electron/workspace-persistence.mjs`（`MAX_BYTES = 12 MiB`，原子替换）→ `safeStorage.encryptString`（`electron/main.cjs:35-40`，Windows 上即 DPAPI）。

这条链路上的两个耐久约束由 §D 的 D3、D9 展开：`agent:begin` 要求待定气泡先落盘（`electron/main.cjs:659-660` 的 `reply` 校验），而队列项移除的保存不等待（`src/App.jsx:949`）。

### E3 上游做了什么我们没跟上

### F1 Cherry Studio（Electron 桌面）

- **它做了我们没做的（**未做**）：多目标、按目标独立调度的自动备份。** [`src/main/services/AutoBackupService.ts`](https://github.com/CherryHQ/cherry-studio/blob/main/src/main/services/AutoBackupService.ts)（18,026 B）里四类目标各自一套键与间隔（`:42-45` local/webdav/s3/nutstore 的 `*.auto_sync` / `*.sync_interval`），调度状态按目标持久化（`:34-35` `auto-backup:` 前缀、`backup.auto_sync.last_attempt_times`），失败分类 `:27 classifyBackupFailure`，服务停止时 `:124` 用 AbortController 取消。我们只有「保存屏障 + 加密落盘」，没有异地/定时备份——用户误删工作区就是永久丢失。
- **它做得比我们好的（**部分**）：更新器的版本与通道纪律。** [`AppUpdaterService.ts`](https://github.com/CherryHQ/cherry-studio/blob/main/src/main/services/AppUpdaterService.ts)：`:42 classifyUpdateFailure` 把失败分成可行动类别；`:261` 把「feed 版本 ≠ 已装版本」当作「被撤回」而不是「已最新」；`:306-323` 显式 `allowDowngrade=false`、`disableDifferentialDownload=false`、按通道加请求头；`:165` NSIS 指定 `installDirectory`。我们 `electron/main.cjs:237-250` 只有事件到 UI 的转发，错误原文直接给用户（D22）。
- **适不适合我们：备份值得做，更新器三项校验立刻可做。** 本地目录备份能复用现有加密桥与定时任务，1–2 天；webdav/s3 各 3–5 天且要先解决凭据存放与脱敏。更新器的 feed 版本校验 + `allowDowngrade=false` 是半天的事。**不要照抄它的一点**：[`electron-builder.yml:126`](https://github.com/CherryHQ/cherry-studio/blob/main/electron-builder.yml) 把 `verifyUpdateCodeSignature` 设为 `false`（`:121-126` 同时有自写 `win-sign.js`、`signExts: [.node]`）——我们本来就未签名，没有 `publisherName` 可校，但也不该主动关校验。

## 未核对（跨节汇总）

以下条目是「读到了疑点、没验到底」，按可疑度排序，后续审计从这里接（各节的详细清单保留在 `docs/audit/*.md` 的「未核对」小节）：

1. **Electron 44.11.5 内置的 Node 版本**：决定 0.2.3 线（要求 ≥24.22.3）能不能上；`scripts/pack-runtime.cjs:90` 复制的就是它，本轮未读到（04·未核对 1，与 D8 同一件事）。
2. **`harness/native-project-fs.mjs` 是否被内核端到端用例间接覆盖**：没有直接单测（D6），`kernel-native.test.mjs` 可能经内核路径打到它，但没跑过一条针对它的断言（02·未核对 1）。
3. **D1 的字符面是否穷尽**：只验了 U+3164 / U+115F / U+FFA0 / U+FE0F / U+E0100 五种；U+2064、U+180B–180D、U+E0020–E007F（标签字符）、U+FFF9–FFFB 是否也能穿过，没逐一试（02·未核对 2）。
4. **完全访问档下审批是否真的弹给用户**：内核策略 `ask` 与客户端只接受 `allowed-once|rejected` 已核实，但没追到「谁在 full 档回答这个请求」（D20、04·未核对 2）。
5. **`electron/browser-service.mjs` 分区会话的权限策略**：只确认 `setPermissionRequestHandler`/`setPermissionCheckHandler` 挂在 `defaultSession`（`main.cjs:818-819`），分区里的 `WebContentsView` 是否继承没追（02·未核对 3、D15）。
6. **`electron/privacy-gateway.mjs`(146) 的长流与并发**：只有 `privacy-gateway.test.mjs` 3 例 + `assistant-stream` 覆盖，SSE 分块边界在真实长流下的还原一致性没验（02·未核对 4）。
7. **`electron/deliverable-access.mjs` 的 HMAC 密钥来源与轮换**：`readVault`/`readBridge` 的密钥从哪来、何时轮换，没追到生成点（02·未核对 6）。
8. **`electron/mcp-config.mjs` 的 `mcpServerIdentity` 对 stdio 的 `cwd` 兜底**：`process.cwd()` 漂移是否会让同一服务器被判成「新地址」而要求重填凭据（02·未核对 7、D14）。
9. **`src/McpSettings.jsx`(42)**：无任何单测，是否会把凭据回显到 DOM/日志没验（02·未核对 9）。
10. **`dsh-compaction-basic` 的 `maxTokens` 语义**：我们传 `maxTokens = effective headroom`，但 `resolveCompactSpec`（`src/config.ts:140-215`）用的是入参 `reservedCompletionTokens`（04·未核对 4）。
11. **Cherry Studio / LobeChat 是否加密本地库**：两个 tree 里都没搜到 `safeStorage` 实现文件（04·未核对 5）。
12. **Cline 现行 checkpoint 实现位置**：`apps/vscode` 与 `sdk/packages/core` 两处都有 checkpoint 文件，只读了后者（04·未核对 6）。
