## 二、本轮修复

### 对话结构与可用性

- 助手消息统一为工具摘要、回复正文、改动文件、交付文件、详情与操作；改动和交付卡片在该轮结束后展示。
- 使用既有雪中墨竹素材作助手标识；正文、工具、卡片、反馈和操作栏共享左基线，保留中性灰白及深色浅底品牌规范。
- 修复七处未定义 CSS 变量引用，统一使用现有 `--line`、`--surface`。
- Toast 移至顶部并限制尺寸；错误提示仍可持续保留和关闭。
- 反馈备注超过 8192 字节时，“保存”仍禁用，“清除”可正常操作。
- 侧栏按置顶、项目、独立／缺失项目归属会话分配唯一入口；悬空 `projectId` 的旧聊天不会因去重而消失，数据归属不被重写。

### 工具轨迹

`electron/execution-events.mjs` 根据原生 `sourceEventSeqs`／调用关联，向界面输出事件坐标或本机不透明 ID。UI 按运行、子会话和调用 ID 合并 call/result，一次调用只算一次；多个并行工具中某一个结束，不再掩盖仍在运行的工具。

新数据保留状态和耗时，不添加原始参数、完整文件路径、工具结果或错误正文。旧轨迹已经丢失关联信息时不按工具名称猜配，标记“历史结果未关联”。默认展示模型不再只取八条；原有轨迹存储上限没有移除，已有截断明确显示“已保留”。详情与时间线共用同一统计口径。

### 供应商与文件入口

- “恢复全部模型”改为一次 IPC 和一次排队持久化；同时清除旧目录残留的隐藏 ID，不影响其他供应商。
- 全部模型都隐藏时仍能进入恢复操作，目录显示实际 model ID 以区分重名。
- 原生选文件过滤补充 WebP / GIF。后续解析和视觉能力限制沿用现有边界，不表示所有动图都可作为模型输入。
- 删除能力清单里与已注册原生文件能力矛盾的总括性 `native-files: not_integrated` 条目；实际读、写、编辑、补丁和图片能力仍各自报告限制。

### 嵌套目录写入

`office_write_file` 可以保存到尚未存在的多层子目录。路径解析先定位最近已存在的真实祖先，只在既有权限策略授权后逐级创建；创建前后核对根目录和祖先身份、真实路径及授权范围。最终文件仍使用 `wx` 排他创建，同名自动编号另存，保留原件。拒绝、取消、链接置换、目录竞争、最终同名竞争均有回归。

边界：Node 的跨平台路径 API 不提供原子目录句柄相对创建，反复身份核对不能被描述成对任意恶意并发进程的绝对 TOCTOU 防护；授权后失败可能留下本轮创建的空目录。本轮没有新增“完全访问”授权范围，也没有改变脱敏或文件覆盖策略。

### 实测发现的锁竞争缺陷

未修改的 `c2f7588` 上，多进程更新脱敏映射的 R09 测试实际失败。时序是：发布锁目录的原子 rename 遇到竞争者，返回 `EEXIST/ENOTEMPTY`；竞争者在后续 `lstat` 前释放目录，旧实现便把正常竞争错误直接抛出。

修复仅将这两个明确的竞争错误交回重试。`EPERM/EACCES` 仍需存在竞争锁才能重试，没有吞掉权限失败。测试用两个真实子进程控制“竞争发布 → 释放 → 观察错误”的时序，并保留并发写入互斥、状态不丢失与失败清理检查。没有放宽映射内容保护、任务隔离或锁所有权校验。

### 测试目录与工程门禁

两份组件测试改为系统临时目录，退出后清理 profile 和编译产物。可选 `ZHIXING_TEST_EVIDENCE_DIR` 仅保存固定名单的小 JSON 与有界日志；不删除用户历史证据或其它应用目录。

Windows CI 使用一次性 runner 和只读仓库权限，分别运行构建、站点、源码和组件门禁，失败仍标失败并收集小文本日志。它不安装到用户环境、不发布、不打 tag；Windows 源码 CI 即使通过，也不等于 Windows 安装包、真实云端或安装生命周期通过。

### Windows OCR 后续定位与最小修复

独立 `diagnostics/phase-0a-ocr` 分支使用原 worker 的临时插桩副本，只读取合成图片，记录阶段、耗时及退出信息，不记录识别正文。25 秒上限和环境白名单始终未变，没有用重试替换失败样本。

1. [首次 12 样本](evidence/phase-0a/ocr-startup-probe.json)：默认 STA 与 MTA 的串行成功率均为 3/4，成功初始化约 22 秒，不能把 MTA 当作已证实的修复。
2. [细分初始化的四样本](evidence/phase-0a/ocr-initialization-probe.json)：全部在 `New-Object` 编码赋值行停留到超时，尚未进入程序集加载或 OCR。
3. [三个变体的八样本](evidence/phase-0a/ocr-module-loading-probe.json)：原写法总耗时 20.521 / 12.290 秒；直接构造编码对象仍耗时 12.196 / 12.107 秒，延迟转移到 `Add-Type`；显式导入 `$PSHOME` 内置 Utility 模块的四个串行／并发样本在 0.322–0.376 秒完成，全部识别匹配。后两个对照样本仍约 12 秒，结果不支持只用整体暖机解释。

因此只在原 `ocr-worker.ps1` 中增加显式加载内置 Utility manifest 的语句，保持其它产品逻辑。微软文档说明，Windows PowerShell 在缺少 `PSModulePath` 时会构建默认搜索路径，从 PowerShell 7 经中间进程继承该变量反而可能引入不兼容模块，因此没有放宽环境白名单：[官方模块路径说明](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_psmodulepath?view=powershell-5.1)。

这里测得的是首次 Utility 命令发现／自动加载相关的等待；没有采集 PowerShell 内部调用栈，不能进一步宣称具体慢目录或系统扫描器已被确定。这个小改动随后在不带插桩的原完整 Windows 门禁中通过两次验证，源码均为 545/545，原 OCR 问题用例逐项通过；没有增大超时、增加重试或跳过用例。源码增量指纹与后续门禁状态见 [OCR 跟进记录](evidence/phase-0a/ocr-follow-up.json)。
