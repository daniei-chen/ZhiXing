# 知行 0.19.0 · 「待核实」的说明跟着正文一起走

## 问题

0.17.0 把「无法归属的占位符」从整段失败降级成保留正文，但那条说明只存在于气泡下方。一旦导出成 TXT/DOCX、或者用「分享或转发」交给别人，接收方看到的 `【敏感值待核实】` 就只是一个没头没尾的方括号——他无法知道这是应用拒绝还原的占位符，很可能当成用户自己写的字，或者当成内容缺失。

## 怎么改

`src/privacy-warning.js` 增加两个纯函数：

- `exportNote(count, { whole })`：单条回答导出时给「（本段有 N 处占位符无法归属对应任务，已按【敏感值待核实】保留。）」，整段会话导出/分享时给「（本会话有 N 处…）」；`count` 为 0 时返回空串，正文一个字符都不加。
- `sumUnrestored(messages)`：把各条回答上的 `unrestored` 相加，字符串数字也认。

`src/App.jsx` 三处接入，全部在打开审阅弹窗之前拼进正文（弹窗里的 `original` 与 `masked` 都会带上）：

1. `openExport(message)` —— 导出单条回答；
2. `openExport(undefined)` —— 「导出聊天文件」与「复制为文件」；
3. `shareCurrentChat()` —— 「分享或转发…」。

单测从 3 条加到 5 条，新增「导出说明的单段/会话口径」与「处数相加」。

## 边界

- 只在**正文尾部**加一句；没有在每个 `【敏感值待核实】` 后面就地标注，读者仍要靠这句话自己找位置。
- 分享走的是系统分享/复制文件，实际接收方看到什么取决于接收方；我们只验证了审阅弹窗里给出的正文带说明。
- Markdown（Harness 会话）格式没有单独验证尾部说明的位置是否影响渲染；TXT 与 DOCX/XLSX 走同一份 `original`。
- 说明本身不进隐私规则统计，也不会被 `prepareDelivery` 判成敏感内容。
- 安装生命周期本版未重跑，证据仍是 0.17.0 的 53 步（0.14.0 → 0.17.0）。
- `ENOTFOUND` 文案仍未端到端触发（0.18.0 记录的原因不变）；安装器未签名；`visualAcceptance`、`crossWindowsUserDecryption` 仍 `outside_scope`；真实子任务归档仍未通过。
