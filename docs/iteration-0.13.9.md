# 知行 0.13.9 · 网络错误说人话

## 问题

请求失败时，用户看到的是一串技术文本。`fetch failed`、`401`、`ENOTFOUND api.deepseek.com`——这些信息对排查有用，对用户没用，因为他不知道该改什么。

之前 `errorText()` 只剥掉 IPC 前缀就原样显示，整个 `src/` 里找不到任何网络错误的中文文案。

## 改了什么

在 `errorText()` 里加一层转换，按「用户能做的下一步」归类：

| 匹配到 | 显示 |
| --- | --- |
| `401` / `unauthorized` / `invalid api key` | API Key 无效或已过期，请在「设置 · 供应商」中更新后重试。 |
| `403` / `forbidden` | 服务端拒绝了这次请求（403），请检查 API Key 权限或账户状态。 |
| `429` / `rate limit` | 请求太频繁（429），请稍等再试。 |
| `ENOTFOUND` / `EAI_AGAIN` | 解析不到服务地址，请检查网络连接或代理设置。 |
| `ECONNREFUSED` | 服务地址拒绝连接，请确认地址和端口是否正确。 |
| `ECONNRESET` / `socket hang up` | 连接被中途断开，请检查网络后重试。 |
| `ETIMEDOUT` / `timed out` / 超时 | 请求超时，请检查网络后重试。 |
| `certificate` / `CERT_` | HTTPS 证书校验未通过，请确认服务地址可信。 |
| `fetch failed` / `network error` | 网络请求失败，请检查网络连接或代理设置。 |

**匹配不到的一律保持原文**，不做猜测性改写——把没认出来的错误硬套成"网络问题"会误导排查。原始文本仍然写进诊断日志。

## 顺带确认的一件事

没配供应商时点发送，`App.jsx` 会直接打开「设置 · 供应商」，不会发一个注定失败的请求。这条原本就有，本轮确认它工作。

请求侧有 90 秒超时（`AbortSignal.timeout(90000)`），超时后落到上面的超时文案。

## 结果

源码回归 364 项、363 通过、0 失败、1 条件跳过；目录包回归 322/323、0 失败、0 取消；Windows 桌面专项 5/5。启动 10 次中位数 815 / 906 / 1,072 ms（上一版 876 / 1,000 / 1,178）。

依赖审计与上一版一致：1,162 个包，0 high、0 critical、32 moderate、2 条 unique 通告。

## 边界

**文案映射没有在真实网络故障下实测**。本轮验证覆盖了构建、包内回归和桌面专项，但没有构造真实的 401、DNS 失败或超时去确认用户界面最终显示成什么样。逻辑是按错误串匹配的，匹配正确性可以推演，端到端表现还没有证据。

真实云端（真实 Key、真实服务端行为）依然未覆盖。签名仍未验证（无证书）。
