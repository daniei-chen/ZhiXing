# 知行 0.14.6 · 安装器留在临时目录里的卸载器副本

这轮从待办池取的是「安装器残留进程」。先量，再改。

## 量出来的东西

关闭应用、不装任何东西，直接看本机状态：

| 项 | 结果 |
| --- | --- |
| 安装器/卸载器残留**进程** | 0（`elevate`／`nsExec`／`Un_A`／`Au_` 都没有） |
| 默认安装位置 `%LOCALAPPDATA%\Programs\office-agent` | 不存在（0.14.5 那次装错位置已卸载干净） |
| `%TEMP%\~nsu.tmp` | **存在，209,663 字节，里面是 `Un_A.exe`，写入时间 20:13Z 后一直留着** |
| `%TEMP%\ns*.tmp` | 12 个、合计约 5.5 GB，但里面的 `app-64.7z`、`Antigravity.exe` 等说明**大部分是别家应用**的 NSIS 安装器留下的，不能算到知行头上 |

所以本轮只处理一件能证明是自己的事：`~nsu.tmp` 是 NSIS 卸载器运行前把自己复制过去的地方，正常退出会删掉；知行 0.14.5 卸载后它没被删，一直占着 200 KB。

## 怎么改

新增 `electron/temp-hygiene.mjs`，启动时（`app.isPackaged` 且不阻塞启动）检查 `%TEMP%\~nsu.tmp`，三条判据缺一不可：

1. **目录名**必须是 NSIS 固定的 `~nsu.tmp`；
2. **里面的可执行文件字节里要含 UTF-16 的「知行」**（或 UTF-8 的 `zhixing`）——别家应用的 NSIS 卸载器也用同名目录，凭名字删会误伤；
3. **目录至少 10 分钟没被写过**，避免和正在进行的安装/卸载抢文件。

三条都满足才整体删除并记 `temp.hygiene`（带 `bytes`、`files`、`reason`）；任一条不满足只返回原因，不动文件、不报错。清理失败只记 `temp.hygiene-failed`。

## 结果

- 源码层：`npm test` 384 个（383 通过、1 跳过、0 失败），新增 5 个用例把三条判据和真删/不动/缺目录都钉住。
- **实包层**：`npm run test:temp` 两个场景都过——带产品名的旧副本被删（日志 `bytes:262 files:1`），别家应用的同名目录原样保留，且不记清理事件。
- **真实机器**：0.14.6 打包构建在 21:28:36Z 的一次实包验收运行里，删掉了本机那个**真实的 209,663 字节** `~nsu.tmp`，日志落在该次运行的 `app.log`。用户环境首次启动 0.14.6 时它已经不在，所以没有第二条清理记录——这是真实情况，不是没生效。

## 边界

- 只处理 `~nsu.tmp` 这一种残留；`%TEMP%\ns*.tmp` 里约 5.5 GB 的目录大多属于别家应用，**本版不声称清理它们**。
- 判据依赖可执行文件里嵌了产品名；如果将来卸载器 stub 不带这两个标记（例如换了打包器），清理会自动放弃——那时需要重新核对，不能沿用这条结论。
- 10 分钟窗口内卡住的副本不会被清理，要等下次启动。
- 「卸载器为何没删掉自己」的根因没有查明（可能是杀软占用或子进程未退出），本版只做兜底清理。
- 只在 Windows x64 验证；安装器仍未签名；真实云端未覆盖。
- 本轮没有触达安装生命周期（0.14.5 刚跑过，安装器逻辑未改动），`historical-upgrade` 仍是 `not_run`。
