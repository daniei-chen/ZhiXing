# 知行 0.12.10 · 启动诊断与可测量性

本轮没有给出可证实的启动提速。工作集中在把启动变成可测量、可定位的问题，同时记录一次被数据否决的优化尝试。

## 交付

- **启动阶段追踪。** 设置 `ZHIXING_STARTUP_TRACE=1` 后，主进程把各阶段耗时写到 stderr：模块加载、`initialise` 的导入、状态、内核、自动化、服务五个阶段，以及窗口显示。未设置时该函数不做任何事。
- **启动测量工具。** `node scripts/probe-startup.mjs <应用路径> <次数>` 用一次性档案启动打包应用，等到输入框可编辑，同时报告渲染进程时间线与主进程阶段耗时，并给出中位数。
- **重复读取修复。** `initialise` 曾把同一个 `config.json` 解析两次，现在只读一次，设置与内核在同一分支应用。
- **首帧显示。** 窗口改为在 `ready-to-show` 显示，`loadURL` 完成后兜底，不再等整个文档加载完成。

## 实测

Windows x64 目录包，5 次启动取中位数：

| 指标 | 中位数 |
| --- | --- |
| 进程创建到可交互 | 1,281 ms |
| 进程创建到调试端口 | 1,039 ms |
| `initialise` 完成 | 1,017 ms |
| 窗口显示 | 1,131 ms |

阶段分布（中位数）：导入 173 ms、状态 632 ms、内核 637 ms、自动化 934 ms、服务 1,017 ms。也就是说 `initialise` 占用启动约八成，其中模块导入与状态加载约 460 ms，自动化初始化约 300 ms，浏览器、终端与语音服务约 80 ms；窗口显示后的渲染进程挂载约 150 ms。

`0.12.9` 同一机器的 3 次测量中位数为 1,263 ms。本轮 1,281 ms 与之差异在噪声内，因此**不宣称本轮带来启动提速**。Windows 上单次启动波动可达数百毫秒，比较必须在同一台机器上取多次中位数。

## 被否决的尝试

把 `initialise` 的十八个模块导入与四次加密读取改成一个 `Promise.all` 批次后，模块导入阶段从 173 ms 变成 1,072 ms，整体启动反而慢了约 240 ms。原因是 V8 同时编译大量模块时争抢 CPU，串行加载反而更快。该改动已回退，提交与测量记录保留在仓库历史中，避免以后重犯。

## 范围

本轮不改变审批、脱敏、沙箱、图片、存储与内核行为，源码回归与目录包回归在改动后重新跑过。启动测量只覆盖 Windows x64 打包应用在空档案下的冷启动；带历史档案、带既有会话的启动未单独测量，真实 DeepSeek 服务延迟也未计入。安装生命周期本轮仍未复跑。 [Windows 验收](windows-acceptance-0.12.10.md) · [能力地图](harness-capability-map.md)
