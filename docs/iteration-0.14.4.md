# 知行 0.14.4 · 自动更新的下载缓存不再无限增长

这轮从一件具体的事开始：用户机器上 `%LOCALAPPDATA%\zhixing-updater` 里躺着 **323.6 MB**——一个 `ZhiXing-0.13.8-x64.exe`，从上一个版本下载下来，既没装、也没删，一直留到 `0.14.3`。

## 为什么会留

electron-updater 把下载的安装包放进 `%LOCALAPPDATA%\<app-update.yml 里的 updaterCacheDirName>\pending\`，安装完**不清理**。目录名由打包时生成的 `app-update.yml` 决定，本机是 `zhixing-updater`；同一个用户目录下还有 `office-agent-updater` 这类更早的应用名残留。

三件事叠加成一个不会自己变小的目录：

1. 每次下载都会写一个新文件；
2. 装完不删；
3. 用户一旦选择「稍后安装」，这个文件就再也没有人碰。

## 改了什么

新增 `electron/updater-cache.mjs`，主进程启动时调用一次，删两类文件：

| 判据 | 理由 |
| --- | --- |
| 文件名里的版本 **≤ 当前运行版本** | 已经装过了，再装一次没有意义 |
| 修改时间超过 **7 天** | 版本号解析不出来时唯一的判据 |

边界写死在代码里：

- **正在等待的更新不删**。它比当前版本新，而且刚写入。只要缓存里还剩一个比当前版本新的安装包，它的 `current.blockmap` 与 `update-info.json` 一起保留——删了它们，下次更新校验会失败。
- **没有待装安装包时，元数据一起清**，并把空掉的 `pending` 目录收走。
- **目录名不猜**。只从打包生成的 `app-update.yml` 读 `updaterCacheDirName`；读不到（开发环境、yml 缺字段、字段里带路径分隔符）就直接跳过，不去动 `%LOCALAPPDATA%` 下的任何其他目录。
- **不跟随符号链接**，清理范围不越出缓存目录。
- **失败只记日志**（`updater.cache-prune-failed`），不影响启动；清理是异步的，不在启动路径上。

## 分层验证到哪一层

| 层 | 证据 | 结果 |
| --- | --- | --- |
| 源码 | `tests/updater-cache.test.mjs`：版本解析、版本比较、已装即删、待装保留、过期清理、孤儿元数据、真删与空目录、yml 读取与拒绝越界 | 8 个用例；全量 379 个测试，378 通过、1 跳过、0 失败 |
| 合成运行 | 同一份用例在打包后的应用里跑（`npm run test:packed`） | 331 个，330 通过、1 跳过、0 失败 |
| Windows 实包 | 新增 `scripts/test-updater-cache.mjs`：把 `LOCALAPPDATA` 指到临时目录，预放「已装过的旧版本 + 正在等待的新版本」，启动真实应用，读 `app.log` 再核对磁盘 | 3 个场景通过 |
| Windows 实包（真实安装） | 装到 `D:\应用\知行` 后启动 | `updater.cache-pruned {"files":1,"bytes":2097152}`，旧版本清掉、新版本保留 |
| 真实云端 | 本轮没有涉及（没有可用 Key） | 不适用 |

实包脚本的三个场景：

1. 预放 `0.0.9`（旧）与 `99.0.0`（新）：旧的删除，新的与它的 blockmap、`update-info.json` 全部保留；删除字节数 4096。
2. 只放 `0.0.8`（旧）：三个文件全删，`pending` 目录收走。
3. 缓存目录不存在：启动照常，不记录清理失败。

## 关于那次 323.6 MB 的实话

- **03:15 实测**：`%LOCALAPPDATA%\zhixing-updater` 有 4 个文件、323.6 MB，核心是 `pending/ZhiXing-0.13.8-x64.exe`（323 MB，写入时间 `11-24 19:32`）。
- **04:00 复核**：目录已经空了。在 `0.14.4` 装上之前就被清掉了，**原因没有查明**（可能是 `0.14.3` 启动时的某条更新检查路径，也可能是系统清理；现有日志无法区分）。
- 因此，**「真实 323 MB 残留在本版被清掉」这句话本轮不能成立**。真实安装上的演示用的是我自己放进去的 2 MB 合成文件（`ZhiXing-0.13.8-x64.exe` 文件名、内容为零字节填充），启动后它被删除、日志记录了 2,097,152 字节，事后把合成残留（含那个「99.0.0」占位文件）一并删干净，用户缓存目录现在为空。

## 边界

- **只在 Windows 上验证**。macOS／Linux 的缓存目录规则不同，本轮没有覆盖。
- **7 天保留期没有在实包上验证**：实包场景用的是「已装过的旧版本」分支；过期分支只有源码层用例。
- **没有验证「更新正在下载时启动应用」**：清理发生在启动早期，理论上早于下载，但没有实测这个交错。
- **没有真实更新流程**：没有可用 Key，也没有制造一次真实的 `downloadUpdate`；「待装的新版本被保留」是预放文件模拟的。
- 安装生命周期本轮没有复跑（`0.14.2` 的证据仍只对 `0.14.1` 安装包成立）；安装器未签名。
- 113 个文件的用户档案里，102 个逐字节不变、7 个是 Chromium 缓存、4 个是本应用自己的写入；加密存储的字节变化用「同一份代码打开两份档案」对比，项目 2→2、会话 0→0、草稿 1→1。
