# 知行 0.38.0 · 没有任务在跑的时候，别说「正在执行」

## 解决什么问题

0.36.0 的验收里撞到过一个更早的死胡同：内核进程的退出**没有在 10 秒内被确认**时，这个会话会进入隔离状态（恢复文件保留、不允许再起第二个内核），之后在这个聊天里每次发送都会被拒绝——

> 该会话正在执行，请先停止当前任务。

这句话在两处都是假话：**没有任何任务在跑**，所以没有「当前任务」可停；用户照它去做也停不掉任何东西。真实状态是「上一个内核还没确认退出」，出路只有三条：点界面上的「重试清理」、等几秒再发、或者新建一个聊天。三条都没有出现在那句提示里。

## 怎么改

`electron/runtime.mjs` 增加 `sessionBusyMessage(sessionId)`：同一会话若有 `cleanup_pending`（或关闭已发起但未确认）的记录，就返回真实原因与出路，否则保持原来的「正在执行」句子。四个入口全部改用它：

- `run()`：真正开始执行时的互斥检查；
- `preview()` 的两处（`该会话正在运行`／`该会话正在运行或删除`）；
- `runPrepared()`：发送预览被占用时的提示。

新句子是：

> 上一轮的内核还没确认退出，恢复文件已保留。可以点「重试清理」，或稍等几秒再发一次；新建聊天可以立即使用。

**隔离本身一点没放松**：仍然不确认退出就不复用会话、不删恢复文件、不起第二个内核。这版只改用户读到的那句话，让它与真实状态一致。

## 结果

- 源码层：`tests/runtime-finalization.test.mjs` 19/19。原先那条 `assert.rejects(..., /会话|运行|执行/)` 恰好被旧文案喂饱，改成断言「含『内核还没确认退出』」且「不含『正在执行』『正在运行』『请先停止』」——换句话说，回退这处改动这条用例会红。
- `npm test` 505 项、504 通过、1 跳过、0 失败。

## 边界

- **触发条件仍未复现**。本轮写了 18 轮短对话的探针（`.preview/qa-0.38.0/exit-probe/`），跑完 18 轮一次也没出现收尾失败；上一版的两条门禁（0.35.0／0.36.0）里出现过两次，都在第 8–9 轮。也就是说：失败确实会发，但**我还没有稳定的复现路径**，所以「改完之后更容易恢复」这类话本轮不说。
- 这版**没有改关闭的时序**（仍是 10 秒上限、1s／3s／10s 三次重试、进程真退出后自动重试），没动 `harness.close()` 与 SIGKILL 的先后关系。是否该在优雅关闭超时后更早升级到强杀，牵涉会不会截断内核最后一次历史写入，**没有实验证据就不动**。
- Windows 实包层：这条文案要走「关闭真的超时」才会出现，本轮**没有在实包上造出这个状态**，因此属于「未覆盖」；实包只复跑了既有的门禁（打包 354 项、组件 14/14、站点 4/4）。
- 界面横幅「内核退出尚未确认，该会话暂不能重新执行。」与「重试清理」按钮是既有实现，本轮没改；两者与新的拒绝文案现在是同一口径，但**没有做视觉核对**。
- 切换压缩（`test:model-switch` 5/5）、模型窗口失败文案（`test:model-window` 4/4）本版未重跑，沿用 0.37.0。
