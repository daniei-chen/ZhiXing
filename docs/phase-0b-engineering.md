## 质量门禁与实际债务

默认检查基线之后新增或修改的 JS/CSS，以及明确收编的旧文件。新文本文件与 `package.json` 检查格式；旧文件的局部功能修改不强制整文件格式化。`.gitattributes` 让受检文本在 Windows 也检出为 LF，没有执行历史文件归一化。

质量门禁回归 8/8，维护清单与包来源回归 7/7。门禁本身含会失败的 JSX/Hook、未定义 CSS Token、错误格式、缺失基线、squash 与换行夹具，不以只验证一份配置能加载作为验收。

首次全仓扫描得到 228 条 ESLint 诊断和 405 份格式差异；修正旧退出夹具后为 226 条及 405 份。收编工具时间线脚本时，为八处原有空 `catch` 补齐处理理由，最终为 218 条及 405 份，完整清单分别保留。四条 Hook 规则诊断来自普通回调 `useTemplate` 的命名误判，不能当作四个已复现产品故障。

两处测试清理目录的 `finally` 安全守卫保留精确、有理由的行内例外。Stylelint 对最高思考档位的九层渐变背景达到 CSSTree 匹配上限；没有静默关闭规则，也没有把这一值写成已完整校验。详见 [代码质量说明](code-quality.md)。

## Windows 工作流

源码检查与打包检查分开执行。PR 各触发一次，合入 `main` 后继续检查，避免同一开发分支每次同时重复 push 和 PR 的源码套件。

打包工作流明确检出 PR 的 head，固定 Node `24.19.0`，与仓库现有许可证及捆绑运行时一致；源码工作流的 Node 与 PR 合并提交另行记录，不混用两者的 SHA 或运行时版本。

流程为：锁定依赖安装 → 显式准备锁定 Electron 二进制 → 构建目录包 → 包内源码及 provenance 核对 → 候选 EXE 回归和界面验收 → 从同一目录包装配 NSIS → 记录签名状态、文件数、大小及 SHA256 → 上传有界证据和候选。

每个门禁保留独立退出状态；失败不阻止后续独立门禁收集证据，最终聚合拒绝任何必需步骤失败或未执行。候选安装器可以随失败记录保存供调查，但不能仅凭 artifact 存在宣称验收成功。截图、结果和有界日志单独收集，profile、项目夹具及任意缓存不进入上传目录。

### 首次打包失败与修正

`0692076` 上的源码 CI 两次通过 560/560、组件 18/18、Sites 4/4。但独立打包 run `45828772595` 在构建器查找 `node_modules/electron/dist` 时失败，包内和界面门禁全部未执行，NSIS 未生成。

锁定的 Electron `44.11.5` 没有 postinstall；其入口首次导入时才调用安装脚本下载二进制。之前源码测试的导入隐式完成了准备，独立打包没有经过该路径。修正为显式执行同一锁定依赖的 `install.js`，检查退出码与实际 EXE 存在，不改变依赖版本或放宽脚本权限。

首次失败的检查记录、artifact 指纹和未执行项保留在 [初次打包记录](evidence/phase-0b/windows-packed-initial.json)。后续构建记录还明确区分实际 checkoutCommit 与 GitHub workflow 合并 SHA，并根据每一步结果生成 coverage 字段。

### 第二次打包揭示的两处验收脚本缺陷

`9130781` 的目录包及 NSIS 已生成，包内回归 383/383、网络错误提示 7 项、原生文件审批与导出 5 项通过。工具时间线与 Phase 0A UI 门禁失败，最终 job 正确为红；候选文件存在没有被记作完整验收通过。原始检查、结果与失败截图保留在 [第二次打包记录](evidence/phase-0b/windows-packed-9130781.json) 及其 [原始证据](evidence/phase-0b/attempt-9130781/checks.json)。

- 工具时间线首次真实调用已通过“1 次调用”断言，但刷新回首页后没有重新打开原聊天，因而等待时间线超时。修正为保存完成后记录实际聊天 ID，确认页面发生刷新，再真实点击同一侧栏入口；同时只读核对保存轨迹里 call/result 的关联 ID。没有注入已生成消息或修改产品导航。
- 新 UI 门禁前 7 项通过，第 8 项几何检查的外层模板把 `split('\n')` 展开成字符串里的裸换行，产生语法错误。修正转义后，26 个实际展开的 CDP 表达式通过 Acorn 与 `vm.Script` 解析；原表达式作为负例明确失败。几何断言、真实文件动作、反馈清除和退出检查未放宽，语法检查本身不等于 Windows 重跑通过。

该失败轮次的应用正常退出、临时目录移除均有记录。旧时间线脚本的善后允许强制结束进程，因此它的结果仍不能作为完整关闭或安装生命周期证据。新 UI 脚本则将强制结束、非零退出或临时目录清理失败判为失败。

## 维护范围

新增 `maintenance:inventory` 只统计该脚本所属仓库的 `release`、`.preview`、`.zhixing-pack-check`，拒绝任意 CLI 根目录或删除参数。每项普通文件均标记保留；符号链接、junction 和特殊文件不跟随。路径变化、权限错误和中途消失明确报告，不将失败吞成零占用。

两个原有维护 npm 入口默认加 `--dry-run`，旧删除实现没有在本轮重写。当前 Linux checkout 中三个目标都不存在；这不说明用户 Windows 工作区的 87 GB 已经消失或可以直接删除。
